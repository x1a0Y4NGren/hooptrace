# 2.0 启动性能续验

更新：2026-10-05。应用源码 `f4ffcea946647e532b11ce61bb17bc70fcadd636`，版本 `2.0.0+4`，schema 3、JSON 格式 2 不变。后续文档提交不改变 APK 来源。十次标准动作和连续录屏已完成，绘制预算仍失败，不标记 T1 完成或发布就绪。

## 实现与定位

保留已审核 C 标识、原生／Flutter 的 288dp 画布与 0.78 缩放、48×48 网格、表情保护及约一秒轨迹，没有修改资源或视觉 Golden。

- 增加仅限启用诊断的 Profile 准备区间，包括资源、codec、image frame、deferred framework frame；原 schema 1 帧采集兼容，完整原始记录保留。
- 修复 100ms Timer 与迟到图像 Future 的竞争：用单调时钟拒绝超过期限的图像并释放。原生阻塞即使延迟 Timer，也不能把迟到图像当作标准动作准备成功。
- Android `SurfaceHolder` 观察器排在 Flutter 观察器之后；原生创建／初始 resize 完成后才开始图像与偏好读取。数据库初始化顺序不变。
- Android API31+ 移除系统启动图的默认退出淡出，再恢复 Flutter 系统栏样式。先提交匹配的静止首帧，再等待移除回执，避免动作开头被遮住；API24–30 使用首次 Flutter 显示回执。
- 渲染与展示回执各有 2s 的 Dart 超时；展示不可用时降级淡出，迟到回执不能重新播放。超时不是对阻塞的原生线程实施硬取消。跳过、关闭／减少动画、失败／旧库保护、资源所有权和进程内单次播放保持。

原生 trace 确认：初次 GLES shader 准备会让合并的 UI／platform 线程睡眠，从而推迟 Dart 回调；标准动作的热段主要成本是 GLES 提交和 BufferQueue 回收等待。网格编码、首次首页布局／字形 atlas 和线程调度各自保留，不能将所有长帧归为同一原因。

四份单次 trace 位于下述产物目录的 `native-trace/`、`native-trace-standard-b37c783/`、`native-trace-asynccompose-968e7c0/`、`native-trace-final-f4ffcea/`，含原始 pftrace、SQLite、逐帧 CSV、线程状态及报告。trace 带额外开销，不纳入十次验收。较早两份标准 trace 的准备起点与初次 shader 时序不同，不能从 renderer 准备值直接推断冷启动变快。
